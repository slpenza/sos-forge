# v0.8.3 — Each release sends stevenpenza.com a chart of sos-forge's infrastructure

stevenpenza.com's `architecture` standard (its v0.7.20, drawn on its owner page since v0.7.21) asks each project for a
chart of its infrastructure. Steve asked sos-forge to adopt it.

## What it decides

**The generator is stevenpenza.com's, copied byte for byte.**
- **Where:** `tools/architecture.mjs`, architecture v1.1.0, matching the sha384 pinned in stevenpenza.com's
  `site/shared/manifest.json`.
- **Never edited here.** A change happens in its home, as a new version, and is copied again.

**The AWS parts come from the stack, the rest from a hand file.**
- **Generated:** the generator reads what CDK synthesized. That's the CloudFront distribution, the site bucket, the
  API with its two routes, the Suggest, Hit and Status functions, the five-minute schedule, the two tables, the salt
  secret and outgoing mail, with the edges between them. It reads names, never values: no address, bucket name or
  account ID reaches the chart.
- **`infra/architecture.hand.json`:** what CDK doesn't own.
  - the visitor and the maintainer's computer, where `sos build` and `sos admin` run;
  - the release, GitHub Releases, and the suggestion switch that `sos admin` sets;
  - NOAA's catalog and its mail, stevenpenza.com and Ask & Answer;
  - the seven open-data sources that `docs/data-sources.md` already names.
- **It is committed, so it holds no private value.** The pre-commit hook checks it against `.private-terms`.

**The release draws the chart and uploads it, after the deploy.**
- **Drawn:** `tools/release.sh` runs `node tools/architecture.mjs --project sos --hand infra/architecture.hand.json
  --commit <sha> infra/cdk.out` once CDK has deployed and the help docs are uploaded.
- **Uploaded:** to `architecture/sos.json` in stevenpenza.com's private docs bucket, beside `status/sos.json`. The
  bucket's name is the `SOS_STATUS_BUCKET` secret. `sosforge-deploy-role` has been allowed to write that one key
  since stevenpenza.com's v0.7.20.
- **Never committed.** By hand without the bucket, the chart is drawn and checked, not uploaded.

**A hand edge to something that's gone fails the tests,** before a release, so a stale arrow can't be drawn.

## What it does not decide

- **Drawing the chart.** stevenpenza.com draws it on its owner page.
- **The 360 video recipe.** v0.8.2's record moved it to v0.8.3; it moves to v0.8.4.
- **Ports.** stevenpenza.com is giving each project a block of ten, and sos-forge's is 8040 to 8049. `sos admin`
  still defaults to 8030 until a version moves it.

## Tested

- **`infra/test/architecture.test.mjs`,** on the stack as the release synthesizes it, with a status bucket and a test
  address:
  - the hand file joins the chart with no problems, every expected resource is there, and every box has an arrow;
  - none of the made-up account, bucket or address reaches the chart;
  - a hand edge to a removed construct fails, naming it.
- **`tests/test_architecture.py`:**
  - the generator is v1.1.0's pinned bytes;
  - the release runs it for `sos` after the CDK deploy and uploads it to `architecture/sos.json`;
  - the hand file has the standard's form.
- **By hand:** the real app synthesized and the command line run on it gave 26 nodes and 37 edges, none isolated, and
  none of the made-up private values.
- **Not tested before release:** the upload, which needs the release's role.
- **The suite:** 189 Python tests (with the browser tests required), 27 node tests and 26 infra tests pass.
