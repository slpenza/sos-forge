# v0.4.2 — Ask from the home page, Help as a help desk, and Ask & Answer pinned by a lock file

Until now the site's Help was a plain list of pages and nobody could ask anything: the Ask page never worked and
went in v0.3.1. Ask & Answer v0.19.4 brought help layouts and a question handoff. This version uses them: an ask
box beside "Read the help" takes a question to Help, and Help opens as a help desk with the question box first.
It also replaces how sos-forge pins Ask & Answer. Instead of reading tags out of a clone of a private repo, the
build fetches a pinned release from the API and checks every file against a committed lock.

## What it decides

**`ask.lock.json` pins Ask & Answer, and the build fetches against it.**
- **The lock:** at the repo root, committed. It names the release (v0.19.4) and the sha384 of each of its 7 files:
  `corpus.py`, the panel (`ask-client.js`, `ask-panel.js`, `ask-panel.css`) and the help viewer (`docsite/`).
  stevenpenza.com's `ask` standard reads it. Nothing in the API reports which release a project built with, so the
  lock is the evidence.
- **The fetch:** `fetch_ask` downloads `corpus.py` from `<ask_base>/artifacts/<release>/` and checks it against the
  lock in Python. Then it runs `corpus.py --fetch`, which checks itself and writes every other pinned file or none.
  A release's files never change, so the lock holds until it is moved.
- **Moving the pin is deliberate, never part of a build:** check `corpus.py` against the integrity `GET /ask`
  lists, run `corpus.py --project . --lock <ask_base>`, and commit the lock with the version that moves. That is the
  one step that takes the API's word for a hash. It was done once for this version: the listed and fetched hashes
  matched.
- **What goes:**
  - `site.toml`'s `ask_release` and the `[help]` `release`, both now refused as unknown keys;
  - `release_tree`, `ask_release_files`, `--ask-answer` and `--strict-ask`;
  - the release workflow's checkout of `slpenza/ask-answer`.

  A build with an Ask & Answer base is strict by nature: any fetch or check that fails stops it.

**The API address lives in `site.toml`.**
- `[site] ask_base` is the one place. The build fetches from it, writes it into `config.json`, and `release.sh`
  exports it for the stack's CSP.
- `--ask-base` and `$SOSFORGE_ASK_BASE` still override it. `--no-ask` builds without Ask & Answer, as a fork would.
- It was already public, in every page's CSP and in `config.json`.
- **Retired:** the release workflow no longer needs the `production` variable `ASK_API_BASE` or the secret
  `ASK_ANSWER_KEY`, a deploy key to the private repo. Both can be deleted once this version is live.

**Help is a help desk.**
- `[help]` gains `layout = "desk"` and `ask = { heading, lede, suggestions }`. The build adds them, with the bar,
  title and groups, to a temporary copy of `package.json`, so the committed `askAnswer` block keeps only what the
  corpus needs.
- `corpus.py` builds the pages with `--ask-base`, mounts Ask & Answer's panel on the landing (question box first,
  then the reader's recent and common questions, then the four groups of topics) and writes the panel's scripts
  beside `index.html`.
- **The help theme:** `help-head.html` gains the panel's `--ask-*` colours. The page already set `--doc-*` dark, but
  a reader whose OS prefers light would otherwise have had a light panel on a dark page.

**The home page has an ask box beside "Read the help".**
- `js/ask.js` mounts Ask & Answer's `box(el, {help: '/help/'})` in the hero's button row. It is one field and an
  Ask button, wrapping under the buttons on a phone.
- **What it does:** it never answers in place. It sends the reader to `/help/#ask=<question>`. The question travels
  in the fragment, so it never reaches a server, a log or a Referer. Help asks it once on load and takes it out of
  the address.
- **Its stylesheet:** inserted before the site's, so the site's look wins.
- **The theme:** `site.css` maps the panel's `--doc-*` and `--ask-*` variables to the site's palette.
- **Without Ask & Answer:** a build has no panel files or `askBase`, so the script removes the box's slot and loads
  no stylesheet.

**Tests drive the real release.**
- **Stand-in API:** `test_site.py` uses a stand-in Ask & Answer API, a local server with a fake release and a
  matching lock. It checks:
  - the fetch, and refusing a changed `corpus.py`, a missing lock, or a lock that doesn't pin the panel;
  - the help build receiving the layout, the panel's words and the base;
  - the panel files being copied, and the retired keys being refused.
- **Real release:** `test_browser.py` builds a fixture site against the real pinned release, fetched from
  `site.toml`'s API and checked against `ask.lock.json`. It serves it with CloudFront's two CSPs, the site's and the
  relaxed one under `/help/`. It checks:
  - the box renders with no errors;
  - asking lands on `/help/#ask=How%20do%20I%20make%20a%20movie%20longer%3F`;
  - Help clears the fragment and shows its panel;
  - a build without Ask & Answer has no box.
- **No question is really asked:** the API refuses localhost, so the test's question never reaches it.
- **Network:** without network the real-release test is skipped, except in CI (`SOSFORGE_BROWSER_TESTS=1`), where
  it must run.

## What it does not decide

- **Hosting the API under the site's own domain.** `ask_base` stays the API Gateway address, which the deployment
  names.
- **A pitch for Ask & Answer in builds without it.** Still for later.
- **Asking a real question in the smoke check.** It would cost a model call and count among the common questions.
  The smoke check only requires `/` and `/help/` to load clean.

## Tested

- **`pytest`:** 148 tests, 10 of them in headless Google Chrome, including the real release end to end.
- **Node:** 11 tests. **Infra:** 5 tests.
- **A real `sos site --dist dist` build:** it fetched v0.19.4 and checked it against `ask.lock.json`, then wrote 10
  help files (the 7 topics, `index.html`, `ask-panel.js` and `ask-client.js`) and the three panel files.
  `config.json` has the API base.
- **Screenshots from headless Chrome with the OS set to light:**
  - On the home page, the box sits beside "Read the help", dark. On a phone it wraps under the buttons at full
    width.
  - Help shows the desk layout, dark: "Ask about sos-forge", the lede, the box, then the four groups.
  - Locally the panel says the documentation can't be reached, because the API refuses localhost.
- **After the push:**
  - **Releases out of order:** v0.4.1 and v0.4.2 were tagged and pushed together. GitHub ran v0.4.2's release
    first and v0.4.1's second, so v0.4.1's site replaced v0.4.2's. Both smoke checks passed, because each checked a
    clean site. Re-running v0.4.2's release put it back. From now on, version tags are pushed one at a time.
  - **CI's first browser job failed one test:** the simulator caption test sampled the caption only during a
    0.6-second drag. On GitHub's runner, with software WebGL, the frames hadn't moved on yet. It now waits up to
    15 s for the caption to change after the drag. It passes three runs out of three locally.
- **Not yet tested:** the deployed round trip with a real answer (Steve's first step above).
