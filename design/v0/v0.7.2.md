# v0.7.2 — A switch on sos admin decides where suggestions go, confirmed, without a redeploy

v0.6.1 let suggestions go to a test address set as a deploy variable. Switching between that address and the mailbox
then meant changing a GitHub variable and releasing. Steve asked for the choice to be a setting in admin that he
confirms, so he can test with his own address and switch to sos@ when he's ready.

## What it decides

**One setting in AWS, `/sosforge/suggest/destination`, says `mailbox` or `test`.**
- **Who reads it:** the suggestion Lambda, when it sends. Each running copy reads it at most once a minute, so a switch
  takes effect within a minute.
- **When it's missing,** as it is until the first switch, or can't be read, the suggestion goes to the mailbox. A
  broken switch can't send a suggestion somewhere unexpected.
- **Who writes it:** only `sos admin`, with Steve's own AWS login. The Lambda may read it and can never change it.

**The Lambda may send to two addresses, and no others.**
- **The mailbox:** `sos@stevenpenza.com`.
- **The test address:** from the production variable `SOS_SUGGEST_TEST`. It replaces v0.6.1's `SOS_SUGGEST_TO`,
  which redirected everything.
- **Enforced by IAM:** its `ses:Recipients` condition lists exactly those two. Without a test address, it lists only
  the mailbox.
- **The email agrees:** its To header always names the address it is sent to.

**`sos admin` shows the switch above the datasets.**
- **What it shows:**
  - "Suggestions from the site go to", with the current address in bold;
  - both addresses as the deployed Lambda has them, read from its configuration, so the page shows what is live;
  - with no test address deployed, that choice says so and its button is off.
- **Switching takes two steps:** "Switch to …", then "Send suggestions to … from now on?" with Confirm and Cancel.
  Only Confirm writes the setting.
- **The server refuses:**
  - any value but `mailbox` or `test`;
  - `test` while no test address is deployed, naming the variable to set;
  - a request without the page's token, as every other action does.
- **If the setting or the Lambda can't be read,** the switch says why instead of guessing.
- **While the test address is chosen,** suggestions go straight to it. They aren't stored under `mail/sos/`, so they
  don't appear in the page's Suggestions list.

## What it does not decide

- **The test address itself.** It is Steve's, set as `SOS_SUGGEST_TEST` in the production environment, and kept out
  of the repo and of this record.

## Tested

- **`infra/test/suggest.test.mjs`:**
  - the switch picks the mailbox or the test address;
  - "test" with no test address deployed, or any other value, means the mailbox;
  - the To header names the address the email is sent to;
  - an unreadable switch means the mailbox, and the suggestion still sends.
- **`infra/test/site-stack.test.mjs`:**
  - without a test address the Lambda may send only to the mailbox; with one, to exactly the two;
  - its only SSM permission is `GetParameter` on the switch.
- **`tests/test_admin.py::test_suggestion_switch`:**
  - the state shows the switch and both addresses;
  - "test" is refused while none is deployed, and so is an unknown value;
  - switching writes the setting and returns the new state;
  - an unreadable configuration shows as unavailable.
- **The admin server:** the switch needs the token, and refuses "test" without a deployed test address.
- **The real app, synthesized:** with no test address, with one, and with a malformed one, which stops synthesis.
- **The suite:** 173 Python tests (with the browser tests required), 23 node tests and 23 infra tests pass.
- **Not tested before the deploy:** the aws CLI ports (reading the Lambda's configuration, the SSM setting) and a real
  suggestion reaching the test address.
