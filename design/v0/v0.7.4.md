# v0.7.4 — Private deploy values come from secrets, which GitHub masks in public logs, and Help has no text under 14px in any state

v0.7.3's tag was refused before it deployed anything: `pyproject.toml` still said 0.7.2. A pushed tag never moves, so
this version carries v0.7.3's work (`sos admin`'s test send, design/v0/v0.7.3.md) with what that run turned up.

## What it decides

**Private values reach the release only as secrets.**
- **What happened:** GitHub prints each step's environment at the top of its log, masking secrets and nothing else.
  Since v0.7.0 the release had read two private values as plain variables: the name of stevenpenza.com's private
  bucket and, since v0.7.2, the suggestion test address. Both were readable in the logs of the v0.7.0 to v0.7.3
  release runs of this public repo.
- **What was done, with Steve's approval:**
  - both values are now production secrets, copied without being printed, and the variables are deleted;
  - the logs of those four runs are deleted, and GitHub now answers 404 for each;
  - no earlier release log and no test run log held either value.
- **What can't be undone:** anyone who read those logs while they were up has seen the values.
- **`release.yml` reads `secrets.SOS_STATUS_BUCKET` and `secrets.SOS_SUGGEST_TEST`.** The values are unchanged, so
  the deploy keeps the status publisher and the test address.

**A test keeps it that way.** `tests/test_workflows.py` allows a workflow to read as plain variables only names whose
values may be public: `AWS_DEPLOY_ROLE_ARN`, `SOS_ZONE_ID` and `PYPI_PUBLISH`. Any other `vars.` fails the suite and
names itself, so the next private value has to be a secret.

**Help has no text under 14px in any of the panel's states.**
- **What CI found:** when the API can't be reached, the panel's "Try again" is 13.4px. v0.5.3's floor covered only
  what Help shows before a question.
- **The pinned panel has 22 rules under 14px** at the site's 17px: answers, their sources, the recent questions,
  the error state. `site/help-head.html` now raises every one to 14px.
- **The list follows the pin:** a test reads the pinned `ask-panel.css` and fails, naming the selector, when a rule
  under 14px isn't in the list. A release that adds one is caught when the pin moves.

## What it does not decide

- **A per-project list of private values,** checked before a commit and after a release. That's v0.7.5.
- **Ask & Answer's own sizes.** A 14px floor in the product would make this list unnecessary; asking for it is
  Steve's call.

## Tested

- **`tests/test_workflows.py`:**
  - the reader finds variables and secrets in expressions and conditions, not in comments;
  - every workflow reads only the public names as plain variables, and the release reads the bucket, the test
    address and the upload key as secrets;
  - against v0.7.3's `release.yml` it fails, naming both values.
- **`tests/test_browser.py`:**
  - `test_help_floor_covers_the_pinned_panel`: every rule of the pinned panel under 14px is in the list, and it fails
    naming the selector when one is removed;
  - `test_home_ask_box_hands_the_question_to_help` measures Help again once the refused question leaves the panel
    in its error state.
- **The suite:** 178 Python tests (with the browser tests required), 23 node tests and 23 infra tests pass.
